## *План перехода на obsta-history*

*Целевой протокол задаёт [[Использование Git]]: локальная ветка `obsta-history` хранит снимки и историю тикетов; [[obstagent]] единолично сохраняет этапы А/Б, не переключает ветки и не меняет HEAD или пользовательский индекс. SQLite исключается полностью. Обработка остаётся последовательной. Полные снимки включают сопутствующие пользовательские изменения и не определяют авторство строк.*

### *1. Согласовать ID и совместимость*

- *Принять единое написание `KOL-1`, `KOL-1/1`, `KOL-1/1/3` по примеру из [[Использование Git]]. В runtime-контексте `ticket_id` становится строкой; разбор, сравнение, границы и ссылки используют полный ID. Ник читается из `nickname` в [[Configs/obsta|Configs/obsta.md]] согласно [[Конфигурирование obsta]], проверяется до активации. Предлагаемый допустимый ник — непустая последовательность заглавных латинских букв и цифр, начинающаяся с буквы; ошибочный конфиг даёт диагностику без остановки наблюдения.*
- *Предлагаю отдельную последовательность для каждого ника: следующий корневой номер равен максимуму корневых номеров этого ника в заметках и заголовках всей достижимой `obsta-history` плюс один. Для дочернего — максимуму непосредственных детей конкретного полного родительского ID плюс один. Компоненты сравниваются как числа: 10 больше 9; `1/20` не повышает корневой номер до 20. Удалённые из заметок тикеты продолжают резервировать номера через историю. При первом запуске без новых ID начинаем с 1.*
- *Старые числовые метки сохраняем и распознаём как отдельное прежнее пространство ID; не переписываем человеческие ссылки и не импортируем счётчик SQLite. Поэтому старый 90 и новый KOL-1 могут сосуществовать. Продолжение старого тикета сохраняет его ID. Некорректные или дублирующиеся границы диагностируем, не угадываем их смысл.*
- *В [[Тикеты]] источник ника сейчас не дописан %%дописал, с дефисом%%; там и в [[2026-10-19-which-emoji-to-use]] встречаются варианты без дефиса. До реализации закрепить написание и область счётчика в одном месте. Никнейм различает участников, но одинаковый ник на двух независимых машинах не обеспечивает уникальности %%не страшно%%; общая распределённая очередь из [[2026-10-23-team-work]] в этот переход не входит.*

### *2. Заменить SQLite восстанавливаемой историей*

*В `Sources/obstagent.py` удалить импорт `sqlite3`, `allocate_id(db)`, создание базы и её закрытие. Ввести логические компоненты разбора ID, чтения конфигурации, построения представления тикетов из Git и сохранения снимка. Пока держать их и тесты в существующем файле, без создания новых постоянных файлов.*

*Заметки показывают актуальный диалог; коммиты ветки истории сохраняют его этапы. Предлагаю записывать в тело коммита версионированные машинные поля: полный ID, уникальный ключ отдельной активации, этап А/Б, путь заметки, родительский тикет, результат и идентификатор сессии, если он доступен. Снимок Б дополнительно ссылается на OID соответствующего А. Повторный вопрос в том же тикете получает новый ключ активации, сохраняя ID тикета. Заголовки остаются ровно в согласованном виде: `#KOL-1 ✍️ <запрос>` и `#KOL-1 🤖 <первое предложение ответа или ошибки>`. Убираем переносы и Markdown-курсив из заголовка, задаём понятный резервный текст при пустом ответе.*

*Так метаданные и дерево фиксируются одним коммитом; отдельный файл реестра не нужен. Кэш в памяти допустим, но восстанавливается из заметок и истории; отдельный Git-индекс — только удаляемый кэш файлов. Чтение должно различать отсутствие ветки, которое нормально для первого снимка, и ошибку Git: ошибку нельзя трактовать как пустую историю и заново выдавать занятые номера.*
### *3. Реализовать снимки по [[Использование Git]]*

1. *Все операции выполнять из корня vault, передавать аргументы списком без shell. Отдельный сохраняемый `GIT_INDEX_FILE` размещать среди служебного состояния Git, получать путь с учётом `.git` как файла и worktree. При потере индекса — `read-tree --empty`. Явно исключать этот индекс, его lock, временные файлы obstagent и внутренние пути Git из всех способов добавления.*
2. *Перед каждым снимком обновлять только существующий блок `BEGIN/END OBSTA DEFAULT` в корневом `.gitignore`. Вне блока сохранять текст побайтно; если блока нет, не добавлять его автоматически. Список расширений брать из протокола. Связанные исходники находить по паре `xxx.py.md`/`xxx.py` и полю `Sources`; относительные пути разрешать от заметки, начальный `/` — от vault. Проверять границы vault, экранировать специальные символы правил Git и сохранять пользовательские правила ниже блока. Дублированный или незакрытый блок считать ошибкой подготовки снимка.*
3. *В отдельном индексе выполнить удаление игнорируемых путей через NUL-вывод `ls-files --cached --ignored --exclude-standard` и `update-index --force-remove -z --stdin`, затем `add -A`. Учесть вложенные `.gitignore`, `.git/info/exclude`, глобальные исключения и удаления файлов.*
4. *Прочитать комментарии `# obsta-history: <path>` из корневого `.gitignore`: обрезать только внешние пробелы, начальный `/` перевести в `:(top)`. Искать через `ls-files --cached --others -z -- <pathspec>` без `--exclude-standard`, отфильтровать служебные и недопустимые пути, убрать дубли; существующие файлы и симлинки добавлять через `git --literal-pathspecs add -f -- <имена>`. Не раскрывать кавычки и подстановки; пустое совпадение допустимо. Предусмотреть разбиение большого списка аргументов, не теряя буквальный смысл имён.*
5. *Выполнить `write-tree`, затем `commit-tree` с прежней вершиной `obsta-history` как единственным родителем; первый коммит без родителя. Даже неизменное дерево даёт новый снимок этапа. Продвинуть ref через `update-ref` с проверкой старого OID, для новой ветки — нулевого OID подходящего формата. При конфликте перечитать вершину и повторить подготовку; ограничить число попыток, чтобы конфликт не блокировал наблюдение бесконечно. Сохранение подтверждается только после успешного продвижения ref.*

*Проверять, что `obsta-history` не выбрана в живом vault; также предусмотреть проверку других worktree перед продвижением общей ветки. Не выполнять checkout, reset, amend, обычный commit или push в этом механизме. Любая ошибка подготовки отменяет снимок; следующая попытка заново приводит отдельный индекс в соответствие с файлами и правилами. Проверка конфигурации remote и серверной защиты остаётся отдельной работой [[2026-10-27-git-grooming]], а смысловые коммиты — [[2026-10-23-form-nice-git-history]].*

### *4. Перестроить цикл запроса и восстановление*

*Вместо нынешнего `process()` с коммитом в HEAD и проверкой `(agent)` сделать явные этапы: сигнал → определение тикета/активации → запись границ и статуса → снимок А → агент → ответ или ошибка → снимок Б. Весь путь, включая назначение ID, первую запись и Git до запуска, должен находиться внутри обработки ошибок. Ошибка записи самой диагностики тоже не должна завершать obstagent.*

- *Разбирать границы по всему документу, с учётом кода, экранирования и вложенности. Сейчас `find_commands()` проверяет диапазоны построчно и вообще игнорирует сигналы внутри известных тикетов; этого недостаточно для многострочного диалога и продолжения. В конце тикета, игнорируя конечные пробелы, продолжать тот же ID и сессию. В другом месте применять правило дочернего тикета из [[Тикеты]]; поддержку fork сессии выделить отдельным этапом. Пока он не готов, явно сообщать о недоступности вложенного запуска, сохраняя сигнал и продолжая обработку других заметок.*
- *При ошибке снимка А агент не запускается: это прямое условие [[Использование Git]]. Наблюдение продолжается, запрос остаётся доступным для повторной попытки с прежним ID. Ограниченные повторы Git выполняются без повторного запуска агента и без бесконечного обслуживания одного сломанного тикета; последующие сигналы тоже должны получать очередь.*
- *После завершения агента записывать итоговый курсивный статус и пытаться сохранить Б даже при ненулевом коде или таймауте. Ошибку Б сообщать перед существующей закрывающей меткой; если заметку или метку удалили — только в лог, без их восстановления. Сохранение результата и успешное выполнение запроса учитывать отдельно.*
- *При старте сопоставлять А/Б по ключу активации и читать текущие границы. Б уже существует — не повторять агента и коммит. А без Б означает незавершённую попытку: сначала проверить живой дочерний процесс и состояние заметки; неизвестный исход не даёт права автоматически повторять действия агента. Если результат сохранился в заметке, можно завершить учёт после проверки; если исход неизвестен — оставить ошибку и ждать явного продолжения, обслуживая остальные запросы.*
- *После отказа Б очередной запрос должен сохранять накопленные файлы. Если поздний снимок содержит результат прежнего запроса, записывать эту связь в метаданных и отличать его от точного снимка на момент завершения прежнего агента. Не обещать восстановление потерянного ответа, если до сбоя он не был записан ни в заметку, ни в Git.*

*Важное ограничение требований: при полностью недоступном Git obstagent продолжает наблюдение и диагностику, но запуск исполнителя невозможен до снимка А. Разрешить отладку через агента даже в таком состоянии означало бы отдельно изменить это условие протокола; план сохраняет действующее условие. Снимок нескольких файлов при одновременном сохранении в Obsidian также не является атомарной транзакцией файловой системы.*

### *5. Обновить договор с агентом и перезапуск*

*[[Agent Instruction]] обновлять одновременно с переключением obstagent на новый протокол. Убрать утверждение про монотонный SQLite ID, предварительный `(human)` в текущей ветке и обязанность агента делать `(agent)`; сообщать строковый ID, ключ активации и OID снимка А. Агент выполняет запрос и возвращает результат, obstagent отвечает за статус и снимок Б. В текущем запуске #90 по-прежнему действует прежняя инструкция с обязательным коммитом.*

*В runtime-контексте `human_diff` не передавать. diff в контексте лишний: агенту достаточно запроса, активного тикета и доступа к текущим файлам и связанным заметкам. Diff полезен, если сам запрос касается изменений; тогда агент может получить его по нужным файлам и ревизиям.*

*Получение промежуточных рассуждений и финального ответа потребует потока событий исполнителя: сейчас `runner` ждёт завершения и держит stdout/stderr в памяти. Адаптер должен различать события статуса, финал и ошибку, сохранять только последний промежуточный статус внутри активного тикета и восстанавливать сессию по сохранённой связи. Точный формат событий и resume/fork проверить на установленном исполнителе при реализации. Если fork недоступен, не выдавать новую сессию за продолжение родительской.*

*Права на обычный человеческий текст, курсив результата, создание файлов и границы активного тикета сохранить; не считать чтение связанной заметки разрешением исполнять её старые команды. Полную карту прав и защищённые операции из [[Протокол работы с агентом-исполнителем]] вводить отдельно, явно различая работающие возможности и проект. Нынешняя `atomic_replace()` проверяет текст перед записью, но не устраняет гонку с редактором между проверкой и заменой; не обещать такой гарантии одним переименованием файла.*

*В `restart_requested()` заменить требование нового HEAD и чистого рабочего дерева проверкой завершённого учёта попытки, сохранённого результата в истории и хеша проверяемого исходника. Сохранить `--self-test`, таймаут, повторную проверку хеша и выход 75 между запросами. При отказе проверки обновления оставлять старую загруженную версию наблюдать и диагностировать, не запускать непроверенный код. Git-ошибки и ошибки тикета больше не должны доходить до общего завершения `main()`; Ctrl+C и неисправимое окружение запуска остаются отдельными причинами выхода. Блокировку единственного obstagent сохранить, завершение больше не закрывает SQLite.*
