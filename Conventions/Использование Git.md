## Общие правила

## Основная логика
В качестве базы данных по [[Glossary/Тикет|тикетам]] выступает [[Glossary/Ветка истории|ветка истории git]]. Учёт тикетов — в заметках и `obsta-history`, без SQLite. ID тикета представлят собой ник пользователя и номер, например `KOL-1`, дочерний — `KOL-1/2`; ник берется из `Configs/obsta`. Номер следующий после максимального для ника или родителя, включая историю.

Главный приоритет — продолжать наблюдение даже при ошибках в гите, ошибка любого этапа работы с гитом не должна завершать фоновую работу [[obstagent]]. Агент-исполнитель самостоятельно не делает коммитов в ветку истории, это делает сам obstagent. При этом obstagent выполняет все операции без перехода в ветку истории и без модификации HEAD.

1. При получении сигнала obstagent определяет [[Glossary/Тикет|ID тикета]]. Если сигнал поступил из конца имеющегося тикета, то продолжаем текущий тикет, новый ID не присваиваем. В противном случае ищем максимальный номер (с учетом вложенности, см. [[Тикеты]]) среди имеющихся тикетов, по заголовкам коммитов ветки истории и [[Glossary/Заметка|заметкам]] хранилища. Затем берем следующий ID, формируем метки тикета в заметке и формируем снимок А, то есть коммит, выполняемый перед началом работы агента-исполнителя (алгоритм этого процесса ниже). Заголовок коммита состоит из ID тикета, эмодзи ✍️ и выделенного фрагмента, например, `#KOL-55 ✍️ Почему программа не работает?`.
2. После успешного сохранения снимка А запускается агент-исполнитель. Когда он заканчивает работу, в том числе по ошибке, в тикет записывается ответ агента или ошибка. После этого делается снимок Б (коммит после работы агента-исполнителя) по тому же алгоритму. Заголовок коммита после работы агента начинается с ID тикета, эмодзи 🤖, после чего идет первое предложение ответа агента-исполнителя или сообщения об ошибке (без значков курсива), например, `#KOL-55 🤖 Ты абсолютно прав`.
3. Если в процессе сохранения снимка Б произошла ошибка, она записывается в [[Glossary/Статус тикета|статус тикета]], если метка тикета все еще есть в заметке, если ее уже удалили - это не причина останавливать работу obstagent, пишем только в лог.
4. Работа с остальными, неслужебными ветками, делается по инициативе пользователя, либо, в будущем, через [[2026-10-23-form-nice-git-history]].

## Как делается снимок
Каждое обращение получает ключ активации. В тело коммитов ветки истории записывается JSON: версия, ID тикета и активации, этап, заметка, родитель, сессия, исход; Б также содержит OID А.

Если в живом vault уже выбрана `obsta-history`, сохранение отклоняется без переключения: иначе `update-ref` изменит и HEAD.

Ветка истории не отправляется на сервер git remote, её дополнительно защищаем на уровне GitHub или Gitea запретом на push в эту ветку (проверка того, что это сделано, выполняется отдельно). Это сделано для того, чтобы в эту ветку можно было писать в том числе секреты и локальные настройки, перечисленные в .gitignore.

Для того, чтобы выбрать, что попадает в ветку истории (контролируемые пользователем файлы), а что нет (кэши, временные файлы), в .gitignore предусмотрены специальные комментарии вида `# obsta-history: <path>`. Каждый такой комментарий содержит так называемый obsta-history путь следующего формата:

- синтаксис как у [pathspec из команды git add](https://git-scm.com/docs/git-add/2.37.3)
- пробелы в начале и конце убираются, внутри сохраняются
- кавычки и shell-подстановки не обрабатываются
- рабочей папкой считается корень хранилища

Каждый снимок сохраняется так:

1. *obstagent использует отдельный индекс через `GIT_INDEX_FILE` и сохраняет его между снимками ради кеша метаданных. При первом создании или потере индекса начинает с пустого через `git read-tree --empty`; загружать дерево прошлого коммита перед каждым снимком не нужно. Все следующие команды работы с индексом выполняются с этим `GIT_INDEX_FILE` из корня хранилища.*
2. *Выполняет `git ls-files --cached --ignored --exclude-standard -z`. Полученные пути удаляет только из отдельного индекса через `git update-index --force-remove -z --stdin`. Затем выполняет `git add -A`, подхватывая новые файлы, изменения и удаления. Это учитывает и вложенные `.gitignore`, и `.git/info/exclude`, и глобальные исключения Git; собственное отслеживание изменений правил не требуется.*
3. *Для каждого obsta-history пути obstagent сначала находит совпадающие файлы. Начальный `/` заменяет на `:(top)`: например, `/private/*.md` превращается в `:(top)private/*.md`. Остальные pathspec передаёт без изменения, сохраняя синтаксис Git. Все команды выполняет из корня хранилища с отдельным `GIT_INDEX_FILE`, без shell-подстановок. Для поиска выполняет `git ls-files --cached --others -z -- <pathspec>` без `--exclude-standard`, чтобы видеть в том числе игнорируемые файлы. Вывод разбирает по NUL, удаляет дубликаты и оставляет существующие файлы и символические ссылки внутри хранилища, исключая внутренние файлы Git и служебное состояние obstagent. Каталоги не передаёт в добавление: использует найденные внутри них имена файлов.*

   *Найденные имена добавляет в отдельный индекс через `git --literal-pathspecs add -f -- <имена файлов>`. Здесь имена трактуются буквально: звёздочки и другие специальные символы в самих именах повторно не раскрываются. Если допустимых совпадений нет - не вызывает `add`. Ошибка поиска или добавления отменяет снимок и выводится в статус тикета; отсутствие совпадений само по себе снимок не отменяет.*

4. *Затем `write-tree` и `commit-tree` создают коммит. Родитель — прежняя вершина `obsta-history`; при первом создании ветки родителя нет. Даже при неизменном дереве снимок фиксирует этап обработки запроса.*
5. *`update-ref` продвигает служебную ветку только при совпадении её прежнего OID: `git update-ref refs/heads/obsta-history <новый OID> <прежний OID>`. При первом создании проверяется отсутствие ссылки нулевым OID подходящей длины. Если ссылку успели изменить, obstagent перечитывает вершину и повторяет подготовку снимка с новым родителем; безусловно чужую вершину не перезаписывает. Любая ошибка добавления или `write-tree` отменяет снимок; сохранение подтверждается только после успешного продвижения ветки.*

Если в .gitignore есть блок
```
# BEGIN OBSTA DEFAULT
# END OBSTA DEFAULT
```
скрипт будет вставлять в него сгенерированный список правил. Блок перегенерируется перед каждым созданием снимка и включает в себя следующие правила:

- игнорировать все файлы по умолчанию
- разрешить обход каталогов, затем разрешить обсидиановские файлы
- разрешить конкретные связанные пути: файлы, которые лежат рядом с заметками и называются так же, но без расширения `.md`, например `xxx.py.md` и `xxx.py`; файлы, которые указаны в свойстве `Sources` в любой заметке. Путь в `Sources` считается относительно заметки, а начинающийся с `/` — от корня хранилища, как в [[Принципы arc67]].

Например, для Markdown и двух связанных исходников фрагмент будет таким:
```gitignore
# BEGIN OBSTA DEFAULT
*
!*/
!.gitignore
!*.[mM][dD]
!*.[bB][aA][sS][eE]
!*.[cC][aA][nN][vV][aA][sS]
!*.[aA][vV][iI][fF]
!*.[bB][mM][pP]
!*.[gG][iI][fF]
!*.[jJ][pP][eE][gG]
!*.[jJ][pP][gG]
!*.[pP][nN][gG]
!*.[sS][vV][gG]
!*.[wW][eE][bB][pP]
!*.[fF][lL][aA][cC]
!*.[mM]4[aA]
!*.[mM][pP]3
!*.[oO][gG][gG]
!*.[wW][aA][vV]
!*.[wW][eE][bB][mM]
!*.3[gG][pP]
!*.[mM][kK][vV]
!*.[mM][oO][vV]
!*.[mM][pP]4
!*.[oO][gG][vV]
!*.[pP][dD][fF]
!/Sources/obstagent.py
!/src/helpers.py
# END OBSTA DEFAULT

# User rules below override the generated defaults

# obsta-history: /drafts/local-plan.md

# obsta-history: /private/*.md

# Exclude transient state
/.obsidian/workspace*.json
/.cache/
```

## *Действующий договор версии 1*
*ID, ник и область счётчиков — [[Конфигурирование obsta]]. JSON в теле снимка: `version=1`, `ticket_id`, UUID `activation_id`, `phase=A/B`, `note`, `parent_ticket_id`, `session_id`, `outcome=pending/success/error/interrupted`; неизвестное — `null`. Б содержит `snapshot_a`; дополнительно сохраняются запрос и результат. Поздний Б имеет `late=true`, а следующий снимок с накопленными результатами — `includes_results_of` со списком UUID. Такие снимки не утверждают точное состояние на момент завершения прежнего исполнителя.*

*Проверяются все worktree: выбранная где-либо `obsta-history` запрещает продвижение. Конфликт ref повторяет подготовку до трёх раз. Отдельный индекс, блокировка и удаляемые кэши активаций находятся внутри Git; они и временные `.obsta-tmp` исключены. Отсутствующий ignore-блок автоматически не создаётся; правила вне корректного блока сохраняются побайтно. `Sources` поддерживает YAML scalar, inline list и indented list в frontmatter, пути — относительно заметки или от корня vault при начальном `/`.*

*Б сопоставляется с А по UUID. Завершённые активации не повторяются. Для А без Б проверяется PID и идентичность запуска; живой исполнитель удерживает последовательную очередь. Сохранившийся результат можно учесть поздним Б, неизвестный исход требует явного продолжения. Ошибка А не запускает агента; задержка повторов не мешает остальным сигналам. Ошибка Б повторяет только сохранение. Удалённые заметки и границы не восстанавливаются. Полностью недоступный Git допускает наблюдение и диагностику, но не запуск до А.*
