*Актуальный режим — локальная `obsta-history`, см. [[Использование Git]]. Watcher последовательно сохраняет А, запускает исполнителя, записывает результат и сохраняет Б. Ошибки Git и тикета диагностируются; наблюдение продолжается. Диалоги ниже описывают прежние версии.*

*Запуск из корня vault:*

```sh
python3 Sources/obstagent.py --self-test
sh -n Sources/obstagent.sh
./Sources/obstagent.sh
```

*Обёртка определяет vault по своему расположению и повторяет запуск только после выхода `75`. При прямом запуске `python3 Sources/obstagent.py` этот код требует внешнего повторного запуска. Watcher хранит индекс, кэш активаций, PID/идентичность исполнителя и блокировку внутри служебной области Git. Старую SQLite не читает, не мигрирует и не удаляет.*

*Обновление Python проверяется между запросами: активация учтена снимком Б, хеш исходника совпадает с сохранённым в истории, новая версия проходит `--self-test` за 60 секунд, хеш проверяется повторно. Чистый HEAD не требуется. При провале старая загруженная версия продолжает наблюдение; тот же непрошедший хеш повторно не тестируется. Изменения shell и окружения требуют отдельного перезапуска между запросами.*

*После аварии watcher сопоставляет А/Б по UUID. Завершённое не запускает повторно. Если исполнитель ещё жив и его идентичность совпала, ждёт его завершения. Неизвестный исход требует явного продолжения; сохранённый результат позволяет поздний Б с соответствующими метаданными. LaunchAgent и защита remote в этот переход не входят.*

#17🎬 А launchd тут как-то надо использовать для надежности? Что он даст? ✅ А launchd тут как-то надо использовать для надежности? Что он даст? ✅

*Для перезапуска после изменения кода launchd не обязателен: описанного цикла достаточно. Он полезен, если obsta должна сама запускаться при входе в macOS и работать без открытого Terminal. Для этого подходит пользовательский LaunchAgent: watcher и Codex работают от вашего пользователя, с его доступом к vault и авторизацией.*

*launchd также умеет повторно запускать завершившийся процесс и направлять stdout/stderr в файлы журналов. Но безусловный `KeepAlive` здесь пока опасен: он поднимет watcher и после намеренной остановки из-за ошибки тикета или провала проверки новой версии. `KeepAlive` с `SuccessfulExit=false` тоже не различает такую ошибку и аварийное падение. Сам launchd не проверяет коммит, маркер тикета и исправность новой версии и не делает откат.*

*Я бы начал с LaunchAgent с `RunAtLoad=true`, без `KeepAlive`, запускающего описанный shell-цикл. Цикл отвечает за обновление по коду `75`, launchd — за запуск при входе и работу в фоне. Нужно явно указать абсолютные пути к Python, скрипту и vault, доступный Codex `PATH` и пути журналов: окружение LaunchAgent отличается от интерактивного shell. Это предложение по настройке; сейчас ни LaunchAgent, ни описанный механизм выхода с кодом `75` не установлены.*

*Автовосстановление после аварии стоит добавить отдельно, когда watcher перед продолжением сможет распознать незавершённый тикет и проверить, не остался ли работающий агент. Текущая блокировка защищает от второго watcher, но после гибели родителя этого недостаточно для защиты от второго агента. Тогда можно включить ограниченные по частоте повторные запуски, сохранив остановку для ошибок, требующих участия человека. Для нынешнего bootstrap автозапуск через launchd полезен, автоматический рестарт после любой ошибки я бы пока не включал.*

#23🎬 Расскажи, как это работает ✅ Расскажи, как это работает ✅

*Сейчас механизм уже реализован в [[Sources/obstagent.py|obsta.py]] и [[Sources/obsta.sh|obsta.sh]]. Фразы выше «нужно добавить в Python» и «сейчас такого поведения нет» относятся к прежнему состоянию. Для запуска из корня vault выполните `./Configs/obsta.sh`; скрипт сам переходит в корень vault, поэтому его можно вызвать и по абсолютному пути из другого каталога.*

*Здесь три процесса: shell-скрипт запускает watcher на Python, а watcher по очереди вызывает агента для каждого тикета и ждёт его завершения. Агент может переписать `Sources/obsta.py` на диске: уже запущенный watcher продолжает выполнять загруженную в память старую версию. Новая версия начнёт обслуживать тикеты только после перезапуска.*

*Например, тикет просит изменить watcher. Агент правит Python, отмечает тикет выполненным и делает коммит `(agent)`. После завершения агента старый watcher проверяет результат: есть ли маркер завершения, новый коммит агента и допустимое состояние Git. Незастейдженные изменения других существующих Markdown-заметок допускаются и остаются нетронутыми; незакоммиченные изменения активной заметки, файлов результата, кода, а также новые или удалённые файлы останавливают обработку.*

*До и после сканирования watcher сравнивает SHA-256 своего Python-файла с хешем при запуске. Если файл изменился, он требует успешно проверенный предыдущий тикет и тот же HEAD Git. Затем отдельный процесс запускает новую версию с `--self-test`, используя тот же интерпретатор Python и таймаут 60 секунд. Этот процесс выполняет встроенные тесты. После тестов watcher ещё раз проверяет хеш файла, HEAD и состояние Git, чтобы не передать управление версии, изменившейся во время проверки.*

*Если всё прошло успешно, старый watcher завершает работу с кодом `75`. Перед выходом блок `finally` закрывает SQLite и освобождает блокировку vault. Shell-скрипт получает `75`, повторяет цикл и запускает Python заново — теперь с новым кодом. Номера тикетов сохраняются в SQLite между запусками, пока база во временной директории существует; команды внутри уже назначенных тикетов повторно не запускаются.*

*Любой код завершения, кроме `75`, останавливает shell-цикл: обычное завершение и Ctrl+C дают `0`, ошибка тикета или проверки обновления — `1`. Ошибка тестов и таймаут требуют вмешательства человека; автоматического отката к прежнему коду нет. Изменение одних Markdown-заметок перезапуска не вызывает. При прямом запуске через `python3 Sources/obsta.py` выход `75` завершит процесс, а новый экземпляр нужно будет запустить самостоятельно.*

*launchd в этой цепочке необязателен: shell отвечает за повторный запуск после обновления, а LaunchAgent может отдельно обеспечить запуск при входе в macOS и работу без открытого Terminal. Если сейчас работает старый watcher без механизма обновления, после окончания его тикета нужен один ручной перезапуск через `./Configs/obsta.sh`.*


#24🎬 Продолжай ✅ Продолжай ✅

*Практически переход на этот режим выглядит так: дождаться завершения активного тикета и коммита `(agent)`, остановить прежний watcher через Ctrl+C в его Terminal и запустить `./Configs/obsta.sh`. Останавливать его посреди работы агента не следует: это может прервать выполнение тикета. Если watcher уже запущен через этот скрипт и поддерживает обновление, повторять переход не нужно.*

*Перед запуском можно отдельно проверить текущий Python-код. Из корня vault:*

```sh
python3 Sources/obsta.py --self-test
```

*Эта команда выполняет встроенные тесты, не запускает обработку команд в рабочем vault и не требует остановки действующего watcher. После успешной проверки запуск в Terminal выполняется отдельно:*

```sh
./Configs/obsta.sh
```

*В журнале появится `Watcher started` с PID и путём vault. При обновлении Python ожидаемая последовательность — `Updated source passed self-test; requesting restart (exit 75)`, затем `Watcher stopped` и новый `Watcher started` с другим PID. Если вместо этого есть `Watcher stopped due to an error; restart refused`, нужно читать причину в traceback выше: shell-цикл уже остановился и сам повторять попытку не будет.*

*После ошибки сначала проверьте результат тикета и `git status`: агент мог успеть сделать часть работы или даже коммит до отказа итоговой проверки. Исправление причины и новый запуск watcher не повторяют старый тикет: команды внутри назначенных границ пропускаются. Для продолжения работы нужна отдельная команда вне старого тикета. Если сообщается `Watcher already running with pid …`, второй экземпляр не запустился; следует разобраться с указанным процессом, сохранив блокировку.*

*Автоперезапуск охватывает только изменение `Sources/obsta.py`. У shell-скрипта и окружения запуска нет такой проверки: после их изменения нужен ручной перезапуск между тикетами. И `--self-test` подтверждает только поведение, покрытое встроенными тестами; он не проверяет авторизацию Codex или окружение будущего LaunchAgent.*

*Следующий шаг для работы без Terminal — пользовательский LaunchAgent, который запускает этот shell-скрипт при входе в macOS. Для него потребуются `RunAtLoad`, абсолютный путь к скрипту, `PATH` с Python и Codex и пути журналов; `KeepAlive` пока следует оставить выключенным по причинам выше. В рамках этого продолжения настройка launchd не устанавливалась.*
