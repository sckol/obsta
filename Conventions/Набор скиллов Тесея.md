## Устройство
Данный набор скиллов - адаптация [[Superpowers]] для obsta. Он позволяет реализовывать и обновлять отдельные [[Программный блок|программные блоки]] в соответствие с [[002-configs]].

Название отсылает к кораблю Тесея — древнегреческого мифологического героя: остаётся ли корабль прежним, если постепенно заменить все его части? Так и здесь: реализацию программы можно менять по блокам, сохраняя её назначение и согласованные требования.

Скиллы создаются из снимка репозитория superpowers с применением к ним изменений, которые адаптируют их для использования в [[Glossary/obstagent|obstagent]]. [[Glossary/Скиллы Тесея/Скилл сравнения реализаций|Скилл сравнения реализаций]] является новым по отношению к superpowers.

Кроме скиллов, набор содержит:
- скрипты с хэлперами, необходимыми скиллам в работе
- адаптеры, которые позволяют скиллам вызывать различные функции в агентах-исполнителях, не задумываясь о разнице интерфейсов Codex, Claude Code, Open Code и т.п.
- хуки, которые

Особенности переноса из Superpowers:
- *Файлы. У каждого скилла своя папка `skills/<имя>/` с основной инструкцией `SKILL.md`. Рядом лежат только нужные ему справочники, шаблоны поручений и скрипты. Например, `task-brief` выделяет одну задачу из плана для кодера. Его адаптируем под наш формат `Plans/`. Комплект поставляется вместе с obstagent вне пользовательского хранилища. Сохраняем ссылку на исходную версию Superpowers и лицензию MIT.*
- *Подключение. Когда пользователь ставит задачу в Obsidian, obstagent запускает Codex и передаёт ему общие правила из `Agent Instruction.md` через настройку `developer_instructions`. Текст конкретной задачи передаётся отдельно. Общее правило указывает, когда открыть `using-theseus/SKILL.md` и где он установлен. Этот файл помогает выбрать следующий скилл. Например, при исправлении ошибки Codex открывает инструкцию по диагностике и читает дополнительные файлы по мере необходимости. Для этого достаточно штатного чтения файлов.*
- *Инструменты и подагенты. Из Superpowers берём принцип адаптера — памятки, каким инструментом Codex выполнить действие из скилла, например запустить проверку или вызвать подагента. Оркестратор выдаёт подагентам отдельные поручения по шаблонам. Кодер получает задачу, рабочую папку и список проверок, ревьюер — требования и фактические изменения. Вводный скилл нужен оркестратору для выбора процесса.*
- *Что оставляем в Superpowers. Плагины и манифесты для других сред, установку через маркетплейс и браузерный помощник мозгового штурма. Спецификацию храним в заметке блока, задачи и прогресс — в плане и разделе Working context. После проверок obstagent переносит разрешённые изменения из отдельной рабочей папки Git в основное хранилище. Меню слияния ветки и открытия PR для этого не требуется.*

В Superpowers определены хуки — команды, которые среда автоматически запускает, чтобы подать вводный скилл при старте или после сжатия истории разговора. В Тесее эту функцию выполняет общее правило, переданное через `developer_instructions`, через которое передается [[Agent Instruction]].

### Роль заметки блока
В шалоне [[Building block]] разделы служат разным целям:
- User requirements — устойчивые требования пользователя: назначение, интерфейс, зависимости и обязательные ограничения. Они сохраняются при [[Рефакторинг блока|рефакторинге блока]].
- Specification — проектное решение и критерии приёмки для реализации текущих требований; с этим разделом работает в основном подагент-планировщик.
- Working context — сведения для работы с текущей реализацией: файлы, неочевидные детали, предлагаемые изменения документации и проблемы. С этой частью работает в основном подагент-оркестратор.
### Выбор модели
В конфиге [[obsta]] задаются модель и эффорт по умолчанию для всех типов подагентов:
- [[Подагент-оркестратор]] (главное требование - модель должна четко следовать инструкциям и не бросать задачу на полпути) - `theseus.orchestrator`
- [[Подагент-планировщик]] (должен тщательно продумать шаги) - `theseus.planner`
- [[Подагент-кодер]] - `theseus.coder` или `theseus.coder_light` для более простых задач и `theseus.coder_heavy` для более сложных
- [[Подагент-ревьюер]] (модель желательно должна отличаться от подагента-кодера) - `theseus.reviewer`
- [[Подагент-оценщик]] - `theseus.evaluator`

Подагент-планировщик должен выбрать для каждой задачи между `coder` и `coder_light` в [[План реализации|плане реализации]], а подагент-оркестратор, если подагент-кодер систематически не справляется с задачей, переходит на использование `theseus.coder_heavy`.

## Работа с гитом
### Создание git worktree и веток
Реализация ведётся в [[Git worktree]], кроме небольших правок. При создании нового блока спецификация и план готовятся в основном хранилище до создания worktree; при рефакторинге worktree создаётся до очистки и планирования. Порядок для каждого типа задачи описан в [[Scenarios/002-sources]]. Используется [[Скилл использования worktree]].

Все worktree размещаются в `.worktrees/` в корне основного хранилища, эта папка находится в .gitignore.

Worktree создаётся из всего актуального состояния хранилища, включая незакоммиченные и неотслеживаемые входные документы. За основу берется последний [[Снимок А, Б|снимок А]] текущей задачи.

На один тикет используется один или несколько worktree и отдельных рабочих веток. Используется имя ветки `theseus/<ticket-id>-<slug>` и каталог `.worktrees/<ticket-id>-<slug>`. Например: ветка `theseus/kol-73-worktree-policy`,  каталог `.worktrees/kol-73-worktree-policy`. Используется ID тикета, начавшего задачу разработки; дочерние поручения того же плана сохраняют это имя. ID приводится к нижнему регистру, `/` во вложенном ID заменяется на `-`: `KOL-73/2` → `kol-73-2`. Slug — краткое описание латиницей в kebab-case. 

Продолжение и замечания ревью используют прежний worktree; новый запуск агента сам по себе не создаёт новый. Но альтернативная реализация или новая попытка с очищенным контекстом получает отдельный worktree от зафиксированного исходного состояния, чтобы сохранить прежний вариант для сравнения. Альтернативы и независимые повторные попытки получают свободный суффикс `-2`, `-3` одновременно у ветки и каталога, например ветка `theseus/kol-73-worktree-policy-2`, каталог `.worktrees/kol-73-worktree-policy-2`.
### Работа внутри worktree
Если в подготовленном worktree есть незакоммиченные или неотслеживаемые входные файлы, obstagent до запуска подагентов фиксирует начальное состояние отдельным коммитом. При рефакторинге obstagent очищает старую реализацию, соответствующие разделы заметки блока и планы, затем фиксирует очистку отдельным коммитом до запуска планировщика.

Кодер коммитит изменения кода и тестов своей задачи согласно логике [[Superpowers]].

Оркестратор обновляет разрешённые разделы заметки блока и отмечает прогресс в плане; для ревью он передаёт изменения относительно исходного состояния. После принятия задачи он коммитит отдельным коммитом свои изменения Working context и отметки в плане; перед завершением фиксирует оставшиеся такие изменения. Перед коммитом он проверяет индекс и diff, включая только разрешённые изменения и исключая случайные входные и чужие правки. Это правило Тесея дополняет superpowers.
### Возврат результата
Obstagent при возврате сравнивает результат с исходным состоянием и переносит разрешённые изменения кода, тестов, заметки и плана (в случае [[рефакторинг блока|рефакторинга блока]] - без служебной очистки планов, которая делается для более чистой реализации).

### Завершение worktree
После успешных ревью, проверок и возврата результата obstagent сам удаляет созданный им worktree, если все нужные результаты сохранены. Это правило Тесея дополняет superpowers. При блокере, конфликте или нужных несохранённых файлах каталог остаётся.
### Фиксация в [[Ветка истории|ветке истории]]
Как и для любого тикета, согласно [[Использование Git]], перед началом работы (то есть до вызова всех подагентов и активации скиллов) делается [[Снимок А, Б|снимок А]], а в конце работы - снимок Б.
