### *Что сейчас ломается*

*В [[Sources/obsta.py|obsta.py]] перед запуском выполняется `git add -A`: он забирает все изменения и затрагивает пользовательский staging. После запуска происхождение правок определяется по расширению и пути: допускаются только изменения существующих Markdown-файлов вне результата. Поэтому новая человеческая заметка вызывает ошибку, а правка активной заметки после успешного коммита выглядит как незавершённая работа агента. Это видно в сообщениях об ошибках у тикетов #17 и #18. Расширять список допустимых Git-статусов недостаточно: Git не знает автора незакоммиченной правки.*

*Есть и отдельные окна отказа: разметка тикета и стартовый коммит выполняются до `try`; после ошибки watcher дописывает сообщение без собственного коммита; следующая задача может записать этот остаток как `(human)`. Проверка последнего названия коммита также не доказывает, что нужный результат и маркер находятся именно в нём.*

### *Кто и когда коммитит*

*Единственный владелец Git-операций — watcher. Агент получает снимок входа и возвращает изменения; создавать коммиты в основной ветке ему не нужно. Watcher отвечает за ID, маркеры, проверки, публикацию результата и восстановление. Это целевое изменение протокола; действующая инструкция пока требует коммит от агента.*

*Обычная задача даёт два коммита: `(human) ticket N: <суть запроса>` перед запуском и `(agent) ticket N: <суть результата>` после проверки. Первый сохраняет накопленные человеческие изменения и активацию команды, второй — только результат задачи, включая точную замену её маркера. Авторство в префиксе означает происхождение содержимого, а не того, кто выполнил команду Git. Дополнительные коммиты нужны только для новых человеческих правок за время работы или для фиксации сбоя.*

### *Как не мешать Obsidian*

*Агент работает во временной изолированной копии исходного коммита B, включая код и необходимые файлы для проверок. В живой vault он не пишет. Это даёт определённый набор его изменений R относительно B; новые заметки, удаления, переименования и правки кода в Obsidian остаются человеческими изменениями независимо от расширения. Одного отдельного индекса для такой изоляции недостаточно: нужно отдельное рабочее дерево. Его служебные данные не попадают в документы.*

*Когда агент закончил, watcher сначала сохраняет накопившиеся человеческие изменения отдельным `(human) ticket N: edits during run`, если они есть; получаем актуальную основу C. Затем переносит только изменения B → R на C через трёхстороннее сопоставление. Независимые изменения, в том числе в разных местах одной заметки, сохраняются вместе. Пересечение правок одного фрагмента, удаление нужного файла, неоднозначное переименование или изменение самой команды останавливают применение. Конфликтные разделители в живой Markdown не записываем; исходники и результат сохраняем для разбора. Новые команды ждут завершения текущего тикета.*

*Перед записью проверяем ревизии затронутых живых файлов ещё раз. При новом сохранении повторяем согласование, а не заменяем файл старой копией. Нужна координация записи с редактором: существующая проверка `read_text()` перед `os.replace()` оставляет окно гонки, а Git-блокировка Obsidian не блокирует. Пока такой координации нет, для короткого применения результата нужно приостановить редактирование затронутых файлов; гарантировать сохранность одновременной записи в тот же файл одним переименованием нельзя. Остальные заметки можно продолжать редактировать.*

*Коммиты строятся через отдельный индекс из зафиксированных снимков; `git add -A` в основном индексе не используется. Если пользователь уже подготовил staged-изменения, автоматические коммиты приостанавливаются до завершения его Git-операции. Просто оставить старый индекс при движении HEAD нельзя: это создаст обратные staged-изменения. Когда пользовательский индекс совпадает с прежним HEAD и не менялся во время операции, watcher согласует его с новым HEAD, сохраняя последующие изменения рабочего дерева. Конкурентное изменение индекса останавливает публикацию и требует восстановления по журналу. После коммита новые человеческие сохранения могут снова оставить рабочее дерево грязным — это нормально, включая активную заметку и файлы результата. Проверяем содержимое зафиксированного дерева и соответствие журналу операции, а не требуем пустой `git status`.*

### *Границы автоматизации*

*Запись основной ветки сериализуется одним watcher. Перед публикацией проверяются ожидаемые ветка и HEAD; неожиданное движение HEAD, переключение ветки, merge/rebase/cherry-pick или незавершённый конфликт приостанавливают задачу без исправления репозитория за пользователя. Для ручных операций Git watcher лучше ставить на паузу; обычное редактирование документов паузы не требует. Чужие блокировки Git не удаляем; при занятом индексе ждём ограниченное время и сообщаем причину. Автоматических stash, reset, amend, checkout поверх правок, переписывания истории, push и pull нет. Ошибки hooks, подписи и отсутствующая Git identity сохраняются как ошибки, настройки пользователя не обходятся.*

### *Успех и восстановление*

*До первого изменения сохраняем журнал операции вне Markdown: ID тикета, состояние, ветку, исходный HEAD, снимки, пути результата и хеши созданных коммитов. Журнал должен переживать перезапуск; нынешней таблицы ID во временном каталоге для этого недостаточно. Этапы: вход сохранён → агент работает → результат подготовлен и проверен → результат опубликован. Git, SQLite и файлы не образуют общей транзакции, поэтому каждый этап должен распознаваться при повторном запуске.*

*Успех подтверждается конкретным коммитом `(agent)` с правильным ID, ожидаемым родителем, разрешённым diff, точным маркером завершения внутри выбранного тикета и успешными требуемыми проверками. Ревизия, на которой прошли проверки, должна совпадать с публикуемым содержимым; если перенос на C изменил проверяемый код или зависимости, проверки повторяются. Обычный человеческий текст и чужие маркеры сохраняются. Код возврата Codex и название последнего коммита сами по себе успеха не доказывают.*

*При сбое до публикации оставляем ожидание и добавляем краткую курсивную ошибку внутри текущего тикета; служебную запись фиксируем отдельно как `(agent) ticket N: record failure`, если Git доступен. Такой коммит не считается завершением. Если коммит невозможен, ошибка остаётся в журнале и показывается при следующем запуске; новые задачи до восстановления не запускаем. Повторять неудачный коммит можно, повторно исполнять задачу вслепую нельзя.*

*После аварии проверяем журнал и фактическую историю: уже опубликованный результат только подтверждаем, подготовленный сохраняем для продолжения, отсутствие результата не маскируем успехом. Сначала убеждаемся, что предыдущий агент завершён. Частично применённые файлы согласуем со снимками, ничего не откатываем поверх новых правок. Временную копию удаляем только после подтверждения результата или явного отказа от него. Эту политику нужно согласовать с [[Conventions/Запуск и перезапуск obsta|перезапуском watcher]]: следующий тикет и обновление кода разрешены после завершения или разобранного сбоя текущего.*

### *Что проверить при реализации*

*Нужны сценарии: новая заметка во время работы; правка активной заметки вне тикета; конфликт внутри тикета; изменение или удаление файла результата; сохранение сразу после коммита; заранее подготовленный пользовательский индекс; смена HEAD; ошибка hook; авария между записью файлов, коммитом и обновлением журнала. Во всех случаях проверяем сохранность человеческих данных, отсутствие чужих изменений в `(agent)`, отсутствие ложного успеха и повторного исполнения после восстановления. Это критерии будущей реализации; код watcher в рамках обсуждения не менялся.*
