## Problem
Вижу проблемы, связанные с git во многих последних запусках [[Sources/obstagent.py|obsta.py]]. Видимо, возникают краевые случаи. Давай продумаем политику работы с гитом (когда что коммитим и как), чтобы работало надежно и не ломало мой ворфлоу. Например, не знаю, так ли необходимо коммитить (human), или может быть агенту в своей микро-ветке работать, чтобы ему другие не мешали или в worktree, или коммитить только свои маленькие кусочки, или проводить именно агенту коммит, чтобы он смерджить изменения смог если что.
## Discussion
### *Что сейчас ломается*
*◇ В [[Sources/obstagent.py|watcher]] перед задачей выполняется `git add -A` и коммит `(human)`. Это включает все изменения, в том числе уже подготовленный вами staging. Поэтому новая заметка, удаление файла или ваше сохранение активной заметки после коммита агента превращают успешное выполнение в ошибку, которую скрипт выбрасывает, если индекс не чистый.*
### *Сравнение вариантов*
- *Коммит `(human)` перед задачей полезен как исходная точка для сравнения и восстановления, но не обязателен для запуска агента. Название обещает больше, чем гарантирует: Git не знает автора каждого фрагмента. Я бы сохранил снимок перед запуском агента, убрав требование, что это исключительно человеческие изменения.*
- *Маленькие коммиты только агента в общем vault требуют учитывать изменения по фрагментам. `git add file` захватывает также ваши правки в этом файле; `git add -p` не определяет авторство, если правки пересекаются. Для bootstrap это сложнее и менее предсказуемо, чем честно сохранять общий снимок.*
- *Микроветка в том же рабочем каталоге не изолирует файлы и индекс. Переключать её под открытым Obsidian неудобно: видимое содержимое заметок может измениться. Я бы этот вариант исключил.*
- *Отдельный worktree действительно изолирует агента: он работает на закреплённой базе, делает коммит, watcher переносит результат в живой vault. Но незакоммиченные человеческие правки туда сами не попадут; нужен исходный снимок. При возврате надо объединить базу, результат агента и текущее содержимое vault.
- *Разрешить агенту самому коммитить и разрешать конфликты можно, но это не устраняет гонку с Obsidian и делает поведение зависимым от конкретного запуска LLM. Сериализацию Git, сохранение снимков и восстановление лучше поручить обычному коду watcher.*
### Сложности
- *Пользователь сохраняет заметки во время работы. Правка другого файла меняет общий diff, правка того же файла смешивается с результатом агента, правка того же фрагмента может быть перезаписана. Несохранённый буфер Obsidian вообще не виден watcher.*
- *Другие агенты и скрипты могут менять файлы, индекс и HEAD. Общая блокировка действует только на участников, которые её соблюдают.*
- *Текущий агент может писать через shell, генератор или дочерний процесс в обход регистрирующего тула. 
- *Файлы, индекс Git, ссылка ветки и SQLite меняются отдельными операциями. Сбой возможен между любыми двумя шагами; сохранение редактора возможно между проверкой содержимого и записью. Hook, заполненный диск и недоступный Git могут остановить коммит.*
### *Варианты сообщений*
Для начала давай придумаем, как будут выглядеть сообщения. Система со скобочками была так, предварительная, слово ticket еще везде мозолит глаза, дай разные варианты.

*Я бы убрал из видимых сообщений слово `ticket` и разделение по предполагаемому автору. Номер `#34` достаточен для связи с запросом, описание говорит о фактическом изменении. Названия описывают фактические изменения; номер связывает снимок с запросом, эмодзи обозначает этап, а не авторство каждой строки:*

- *#35 ✍️ Воп
- *#35 🤖 Сформулирован краткий протокол сохранения*
### *Что желательно гарантировать в работе*
*Подобно тому, как для СУБД определяют гарантии ACID, перечислим, что можно требовать от подобной системы:*

| *Свойство*                   | *Желаемая гарантия*                                                                                                          |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| *A — атомарность результата* | *Весь подготовленный результат задачи входит в один итоговый коммит; частичный результат не объявляется завершённым.*        |
| *C — согласованность*        | *ID, база, состав результата, проверки, маркер и OID коммита относятся к одному выполнению.*                                 |
| *I — изоляция*               | *Чужие записи не теряются; коммит содержит только результат данного тикета.*                                                 |
| *D — сохранность*            | *Подтверждённый результат доступен после перезапуска; восстановление не создаёт второй коммит и не запускает агента заново.* |
| *Полнота*                    | *Все предназначенные для Git результаты задачи, включая новые и удалённые файлы, сохранены.*                                 |
| *Живучесть*                  | *Ожидаемые ошибки не теряют работу и не валят весь watcher; после устранения причины обработка продолжается.*                |
| *Понятная история*           | *Сообщения описывают фактический diff и содержат ID тикета; отсутствие описания не мешает сохранению.*                       |
### *Что сохраняем и чем уступаем*
Важные приоритеты:
- живучесть: нужно делать так, чтобы obstagent продолжал обрабатывать входящие сигналы, даже если произошла ошибка в его работе, так как отладка этих ошибок будет производиться через него самого
- по возможности все файлы, с которыми работает пользователь в хранилище и которые непосредственно создает агент, должны проходить через контроль версий, хотя бы через локальную ветку
- недопустимо, чтобы в результате какой-то ошибки мы бы систематически теряли бы какие-то файлы в гите, которые должны там быть. Периодическое сохранение в гит не нужно, но нужно чтобы при новом запросе несохраненное бы сохранялось.
- логика работы должна учитывать [[Принципы arc67]], в частности то, что файлы не будут создаваться бесконтрольно

Все остальное уже менее приоритетно. 

## Decision
### Основная логика
В качестве хранилища тикетов использовать не sqllite, а в [[Glossary#Ветка истории|ветку истории]] ветку git `obsta-history`.  Номера задач можем обнулить, к тому же, теперь будет использоваться не только номер, а комбинация "номер+никнейм". Главный приоритет — продолжать наблюдение даже при ошибках в гите, ошибка любого этапа работы с гитом не должна завершать фоновую работу obstagent. Агент-исполнитель самостоятельно не делает коммитов в ветку истории, это делает сам obstagent. При этом obstagent выполняет все операции без перехода в ветку истории и без модификации HEAD.

1. При получении сигнала obstagent определяет [[Glossary|ID тикета]]. Если сигнал поступил из конца имеющегося тикета, то продолжаем текущий тикет, новый ID не присваиваем. В противном случае ищем максимальный номер (с учетом вложенности, см. [[Тикеты]]) среди имеющихся тикетов, по заголовкам коммитов ветки истории и [[Glossary#Заметка|заметкам]] хранилища. Затем берем следующий ID, формируем метки тикета в заметке и формируем снимок А, то есть коммит, выполняемый перед началом работы агента-исполнителя (алгортим этого процесса ниже). Заголовок коммита состоит из ID тикета, эмодзи ✍️ и выделенного фрагмента, например, `#KOL-55 ✍️ Почему программа не работает?`.
2. После успешного сохранения снимка А запускается агент-исполнитель. Когда он заканчивает работу, в том числе по ошибке, в тикет записывается ответ агента или ошибка. После этого делается снимок Б (коммит после работы агента-исполнителя) по тому же алгоритму. Заголовок коммита после работы агента начинается с ID тикета, эмодзи 🤖, после чего идет первое предложение ответа агента-исполнителя или сообщения об ошибке (без значков курсива), например, `#KOL-55 🤖 Ты абсолютно прав`.
3. Если в процессе сохранения снимка Б произошла ошибка, она записывается в [[Glossary#Статус тикета|статус тикета]], если метка тикета все еще есть в заметке, если ее уже удалили - это не причина останавливать работу obstagent, пишем только в лог.
4. Работа с остальными, неслужебными ветками, делается по инициативе пользователя, либо, в будущем, через [[2026-10-23-form-nice-git-history]].
### Как делается снимок
Если в живом vault уже выбрана `obsta-history`, сохранение отклоняется без переключения: иначе `update-ref` изменит и HEAD.

Ветки истории не отправляются на сервер git remote, ее дополнительно защищаем на уровне GitHub или Gitea запретом на push в эту ветку (проверка того, что это сделано - выполняется отдельно, см. [[2026-10-27-git-grooming]]). Это сделано для того, чтобы в эту ветку можно было писать в том числе секреты и локальные настройки, перечисленные в .gitignore. 

Для того, чтобы выбрать, что попадает в ветку истории (контролируемые пользователем файлы), а что нет (кэши, временные файлы), в .gitignore предусмотрены специальные комментарии вида `# obsta-history: <path>`. Каждый такой комментарий содержит так называемый obsta-history путь следующего формата:
- синтаксис как у [pathspec из команды git add](https://git-scm.com/docs/git-add/2.37.3)
- пробелы в начале и конце убираются, внутри сохраняются
- кавычки и shell-подстановки не обрабатываются
- рабочей папкой считается корень хранилища

*Каждый снимок сохраняется так:*
1. *obstagent использует отдельный индекс через `GIT_INDEX_FILE` и сохраняет его между снимками ради кеша метаданных. При первом создании или потере индекса начинает с пустого через `git read-tree --empty`; загружать дерево прошлого коммита перед каждым снимком не нужно. Все следующие команды работы с индексом выполняются с этим `GIT_INDEX_FILE` из корня хранилища.*
2. *Выполняет `git ls-files --cached --ignored --exclude-standard -z`. Полученные пути удаляет только из отдельного индекса через `git update-index --force-remove -z --stdin`. Затем выполняет `git add -A`, подхватывая новые файлы, изменения и удаления. Это учитывает и вложенные `.gitignore`, и `.git/info/exclude`, и глобальные исключения Git; собственное отслеживание изменений правил не требуется.*
3. *Для каждого obsta-history пути obstagent сначала находит совпадающие файлы. Начальный `/` заменяет на `:(top)`: например, `/private/*.md` превращается в `:(top)private/*.md`. Остальные pathspec передаёт без изменения, сохраняя синтаксис Git. Все команды выполняет из корня хранилища с отдельным `GIT_INDEX_FILE`, без shell-подстановок. Для поиска выполняет `git ls-files --cached --others -z -- <pathspec>` без `--exclude-standard`, чтобы видеть в том числе игнорируемые файлы. Вывод разбирает по NUL, удаляет дубликаты и оставляет существующие файлы и символические ссылки внутри хранилища, исключая внутренние файлы Git и служебное состояние watcher. Каталоги не передаёт в добавление: использует найденные внутри них имена файлов.
   
   *Найденные имена добавляет в отдельный индекс через `git --literal-pathspecs add -f -- <имена файлов>`. Здесь имена трактуются буквально: звёздочки и другие специальные символы в самих именах повторно не раскрываются. Если допустимых совпадений нет - не вызывает `add`. Ошибка поиска или добавления отменяет снимок и выводится в статус тикета; отсутствие совпадений само по себе снимок не отменяет.*

4. *Затем `write-tree` и `commit-tree` создают коммит. Родитель — прежняя вершина `obsta-history`; при первом создании ветки родителя нет. Даже при неизменном дереве снимок фиксирует этап обработки запроса.*
5. *`update-ref` продвигает служебную ветку только при совпадении её прежнего OID: `git update-ref refs/heads/obsta-history <новый OID> <прежний OID>`. При первом создании проверяется отсутствие ссылки нулевым OID подходящей длины. Если ссылку успели изменить, watcher перечитывает вершину и повторяет подготовку снимка с новым родителем; безусловно чужую вершину не перезаписывает. Любая ошибка добавления или `write-tree` отменяет снимок; сохранение подтверждается только после успешного продвижения ветки.*

Если в .gitignore есть блок
```
# BEGIN OBSTA DEFAULT
# END OBSTA DEFAULT
```
скрипт будет вставлять в него сгенерированный список правил. Блок перегенерируется перед каждым созданием снимка и включает в себя следующие правила:
- игнорировать все файлы по умолчанию
- разрешить обход каталогов, затем разрешить обсидиановские файлы
- разрешить конкретные связанные пути: файлы, которые лежат рядом с заметками и называются так же, но без расширения `.md`, например `xxx.py.md` и `xxx.py`; файлы, которые указаны в свойстве `Sources` в любой заметке. Путь в `Sources` считается относительно заметки, а начинающийся с `/` — от корня хранилища, как в [[Принципы arc67]].

Например, для Markdown и двух связанных исходников фрагмент будет таким:
```gitignore
# BEGIN OBSTA DEFAULT
*
!*/
!.gitignore
!*.[mM][dD]
!*.[bB][aA][sS][eE]
!*.[cC][aA][nN][vV][aA][sS]
!*.[aA][vV][iI][fF]
!*.[bB][mM][pP]
!*.[gG][iI][fF]
!*.[jJ][pP][eE][gG]
!*.[jJ][pP][gG]
!*.[pP][nN][gG]
!*.[sS][vV][gG]
!*.[wW][eE][bB][pP]
!*.[fF][lL][aA][cC]
!*.[mM]4[aA]
!*.[mM][pP]3
!*.[oO][gG][gG]
!*.[wW][aA][vV]
!*.[wW][eE][bB][mM]
!*.3[gG][pP]
!*.[mM][kK][vV]
!*.[mM][oO][vV]
!*.[mM][pP]4
!*.[oO][gG][vV]
!*.[pP][dD][fF]
!/Sources/obsta.py
!/src/helpers.py
# END OBSTA DEFAULT

# User rules below override the generated defaults

# obsta-history: /drafts/local-plan.md

# obsta-history: /private/*.md

# Exclude transient state
/.obsidian/workspace*.json
/.cache/
```
