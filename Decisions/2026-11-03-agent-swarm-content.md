## Problem
Мы планируем часто переписывать программные блоки с нуля (см. [[002-sources]]), чтобы повышать качество кода. Естественно, будем делать это не при каждом случае, а только когда правка достаточно крупная или спустя время. Тем не менее, хочется достичь высокого качества автономно, при этом не затратив много токенов. Должно быть как минимум два решения: для переписывания (когда мы в отдельном worktree удаляем текущую реализацию и volatile-блок в [[Building block|описании блока]]) и редактирования (обычный режим).

Как называем? Куда помещаем скиллы? Есть ли готовые плагины для этого?
## Discussion
Планирую использовать рой агентов по крайней мере для полного переписывания. Как минимум два участника:
- оркестратор
- реализатор (правильно ли слово? Может, кодер).

Также возможно стоит добавить reviewer, который будет использовать например встроенную функцию review.

#KOL-36🎬 __Насколько это хорошая практика и распространенная? Посмотри в интернете и дай в целом рекомендации. Какие модели для чего использовать и какой effort (стек Open AI)? Использовать ли Plan Mode, Goal mode? План я сам вычитывать не буду, только если агенту он нужен. Как правильно поступать с мелкими правками. Мне кстати нравится, как работают мелкие правки (диагностика и фикс) у Superpowers. Интересуют актуальные рекомендации на конец 2026 желательно.__

*◇ Рекомендую два процесса: один агент для мелких исправлений; оркестратор → реализатор → независимый reviewer для крупных изменений. «Реализатор» — вполне подходящее название. Ниже — рекомендации по проверенным источникам на 3 ноября 2026; изменения до конца декабря пока подтвердить нельзя.*

*Связка реализации и независимого review — уже поддерживаемый инструментами подход: она описана в [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents) и [Superpowers](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md). Однако наличие таких инструментов не доказывает, что рой экономичнее одного агента. OpenAI прямо предупреждает о дополнительном расходе токенов. Начинать лучше с небольшой команды и расширять её по результатам своих задач.*

*Частое переписывание с нуля я бы оставил экспериментальным режимом. В изученных источниках нет оснований считать его общепринятым способом повышения качества. Оно оправдано, когда реализация мешает выполнить конкретные требования, а контракт блока достаточно полон. Само по себе время с последней переписи — слабый критерий: можно потерять накопленные исправления и совместимость.*

*Для крупной задачи в obsta предлагаю такой порядок:*

1. *Оркестратор проверяет Stable: публичный интерфейс, ограничения, наблюдаемое поведение и критерии приёмки. Готовит короткий рабочий план и задания агентам.*
2. *Реализатор пишет код в отдельном worktree и запускает проверки. Для одного связного блока достаточно одного реализатора; параллельная запись полезна только при независимых границах файлов и интерфейсов.*
3. *Reviewer получает требования, итоговый код, diff и результаты проверок. Проверяет соответствие контракту и ошибки реализации; возвращает конкретные дефекты с обоснованием. Встроенный `/review` можно использовать для проверки diff, дополнив его проверкой требований.*
4. *Реализатор исправляет подтверждённые дефекты; reviewer повторно смотрит затронутые места. Для старта я бы ограничил цикл двумя проходами, затем требовал пересмотра причины затруднений. Это моя рекомендация для контроля расходов.*

*При переписывании важно сохранить независимые приёмочные проверки. Их можно подготовить по старой реализации до её удаления и запускать отдельно, не раскрывая реализатору старый код. Иначе агент может одновременно неверно понять контракт и написать подтверждающие это тесты. Также worktree сам по себе не скрывает старую реализацию: она остаётся доступной через Git. Строгое исключение доступа потребует отдельного ограничения среды.*

*Модели и effort: следующая раскладка — предлагаемые стартовые настройки для obsta, а не измеренный оптимум. Официальные роли моделей подтверждены в [OpenAI Docs](https://developers.openai.com/api/docs/guides/latest-model).*

- *Механические изменения с точным заданием, поиск и извлечение контекста: `gpt-6-luna`, `high` для работы с кодом; `low` для простой классификации или извлечения.*
- *Обычные багфиксы и реализация: `gpt-6.1-sol`, `medium`. Неочевидная диагностика, интеграция нескольких частей — `high`.*
- *Оркестратор крупной задачи: `gpt-6.1-sol`, `high`. Архитектурная неопределённость и сложные тупики — `gpt-6-astra`, сначала `low`, повышать по необходимости.*
- *Reviewer: `gpt-6.1-sol`, `high`; для особо сложных изменений конкурентности, безопасности или сохранности данных — Astra.*
- *Редактура заметок и визуальные задачи: `gpt-6.1-terra`, `medium`; отдельная специализация для основного кодера здесь не нужна.*

*`xhigh` и `max` оставил бы для задач, где сравнение результатов оправдывает дополнительные затраты: так рекомендует [OpenAI](https://developers.openai.com/api/docs/guides/deployment-checklist). Модель и effort дочерних агентов лучше задавать явно, чтобы они случайно не наследовали дорогие настройки оркестратора. Сравнивать стоит стоимость успешно завершённой задачи, число повторных исправлений и время, а не только цену токена.*

*Plan Mode по умолчанию вам не нужен: он предназначен для подготовки плана перед реализацией \([документация](https://learn.chatgpt.com/docs/developer-commands?surface=cli)\). Если вы план не читаете, агент может вести краткий рабочий план в обычном режиме и сразу исполнять его. Для долгой задачи полезно сохранять этапы, принятые решения и результаты проверок, чтобы переживать сжатие контекста.*

*Goals полезны для длительного цикла с проверяемым финишем: миграции, переписывания блока, поиска плавающего бага, оптимизации. Задавайте результат, проверки, границы и бюджет. Например: «Реализовать блок по Stable; пройти перечисленные приёмочные проверки; менять только разрешённые пути; при исчерпании бюджета сообщить остаток». Для одиночной правки достаточно обычного запроса. Goals поддерживают продолжение между ходами, но их доступность и работу в запуске через obstagent нужно проверить отдельно; интерактивный `/goal` не гарантирует такую интеграцию. [Источник](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex).*

*Для мелких багфиксов я бы перенял ядро [Superpowers systematic-debugging](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md): воспроизвести → установить причину → проверить одну гипотезу → минимально исправить → повторить воспроизведение и релевантные проверки. Один агент, без отдельного оркестратора, Plan Mode и Goal. Для бага полезен регрессионный тест; опечатке достаточно проверки результата. После трёх неудачных исправлений Superpowers предлагает остановить перебор и обсудить архитектуру. Маленький diff с неизвестной причиной или риском потери данных следует сразу считать сложной задачей.*

__То есть нужен мне отдельный агент reviewer или нет? Что кстати дает review mode в codex, он точно мне применим или лучше скилл писать?__

*◇ Для переписывания блока — да, рекомендую отдельный запуск reviewer после реализации. Для обычной мелкой правки — по необходимости. Постоянно работающий третий агент не нужен.*

*Встроенный review Codex уже выполняет роль проверяющего: изучает выбранные изменения и выдаёт приоритизированные замечания, не исправляя код. Поддерживает незакоммиченные изменения, сравнение с базовой веткой, отдельный коммит и собственные инструкции. Это применимо локально, без GitHub. [Документация](https://learn.chatgpt.com/docs/code-review).*

*Для obsta я рекомендую небольшой скилл, который запускает отдельную проверку и задаёт её условия:*

- *Передаёт Stable, ссылки на требования, границы блока и результаты тестов.*
- *Требует проверить соответствие контракту, пропущенные сценарии и конкретные ошибки; для замечания — условие возникновения, последствие и место в коде.*
- *Возвращает замечания оркестратору; реализатор исправляет подтверждённые проблемы. Reviewer сам код не меняет.*

*Скилл и review mode здесь дополняют друг друга: скилл описывает ваш процесс, встроенный review выполняет проверку кода. Если нужна подробная проверка каждого пункта Stable с отдельным вердиктом, удобнее обычный агент в новой сессии с таким заданием: стандартный review ориентирован на список дефектов, и отсутствие замечаний ещё не подтверждает полноту реализации.*

*Есть существенная особенность вашего vault: `--uncommitted` захватит также человеческие и посторонние изменения. Поэтому проверять лучше изолированный worktree либо явно заданный набор файлов и diff. При полном переписывании reviewer должен читать весь итоговый блок и контракт.*

*Проверил установленный CLI: доступны `codex review` и `codex exec review`, у последнего есть `--json`. Текущий obstagent запускает обычный `codex exec`; автоматического этапа review в нём пока нет. Мой выбор для вас: отдельный запуск reviewer, управляемый коротким скиллом; встроенный review использовать внутри него там, где достаточно проверки изменений.*

__Как назвать скилл? Хочу что-то вроде throwaway, мне нужно обязательно что-то на t. Дай красивые варианты.__

*◇ Я бы выбрал ` Theseus` → `theseus`: корабль Тесея — реализация меняется целиком, а контракт и идентичность блока сохраняются. Красивая метафора именно для вашего процесса.*

- *`tinder` — трут: из небольшого описания разгорается новая реализация. Звучно, но сильная ассоциация с приложением знакомств.*
- *`turnover` — смена, обновление: одна реализация уступает место другой. Ближе всего по духу к throwaway.*
- *`transmute` — превращать: из прежней формы возникает новая, при этом сохраняется суть.*
- *`tabula` — от tabula rasa, «чистая доска»: писать заново по Stable.*
- *`tempest` — буря: выразительное название для роя агентов и радикальной переделки.*
- *`tessera` — элемент мозаики: красивое название для работы с отдельными блоками.*
- *`throwaway` — тоже удачно, если главный принцип — готовность выбросить реализацию. Но в английском есть оттенок одноразовости и небрежности.*

*Мои фавориты: `theseus` — по смыслу, `tabula` — по лаконичности, `tempest` — по звучанию.*

Помимо плагина использует собственный CLI `omx`; командный режим опирается на tmux. Для вашей задачи я бы начал с Superpowers: у OMX больше инфраструктуры, которую придётся согласовать с obstagent.*

*Моя рекомендация: взять готовый процесс Superpowers за основу, а Theseus оставить короткой инструкцией для особенностей obsta: Stable как контракт, пересоздание одного блока, независимая приёмка, ограничения доступа к старому коду и правила переноса результата. Обычный процесс Superpowers включает согласование дизайна и плана с человеком; для вашего неинтерактивного запуска этот этап нужно адаптировать. Также сохранить запрет коммитов и правила человеческого текста.*

__Есть ли другие варианты? Которые бы более точно соответствовали бы задаче?__

*◇ Да, нашёл более узкие варианты. Прежнее «Superpowers — самый подходящий» было слишком категоричным: выбор зависит от того, нужен ли отдельный реализатор или достаточно независимого review.*

- *[cxc-loop](https://github.com/willagio/cxc-loop) — ближе всего к компактному циклу «реализовать → проверить → исправить». Работает внутри Codex; reviewer может быть Claude, отдельный Codex в чистом контексте или оба. Есть ограничение числа циклов; плагин не делает коммитов и не трогает staging. Ограничения: основной агент одновременно оркестратор и реализатор; worktree нужно подготовить отдельно; отдельного контроллера для headless-реализации нет. Для обычного редактирования это первый кандидат на пробу, но интеграция с obstagent требует проверки.*
- *[review-loop](https://github.com/NYTC69/review-loop) — ближе к отдельному управляемому процессу: программный координатор, автор, независимый reviewer, дополнительная проверка и возврат на исправления. Есть плагин Codex. Режим `--lifecycle-mode off` ограничивает процесс планированием, реализацией и финальной проверкой, возвращая незакоммиченный результат. Однако по умолчанию используются и Codex, и Claude; завершение предусматривает явную приёмку человеком. Для вашего полностью неинтерактивного запуска потребуется адаптация.*
- *[codex-subagent-execution](https://github.com/Bang-isme/CodexAI---Skills/blob/main/skills/codex-subagent-execution/SKILL.md) — готовый скилл именно со схемой «оркестратор → отдельный реализатор → проверка требований → проверка качества → исправления». Это наиболее точное совпадение по ролям, но фактически близкий родственник подхода Superpowers. В инструкции предусмотрены согласованный план и коммиты — эти части для obsta нужно изменить.*

*Для Theseus целиком готового совпадения среди проверенных решений я не нашёл: ни одно не описывает ваш процесс пересоздания одного блока по Stable с удалением старой реализации, независимой приёмкой и обновлением Volatile. Поэтому моя рекомендация теперь точнее: для редактирования испытать cxc-loop с Codex-reviewer; для переписывания сохранить Theseus и заимствовать шаблоны ролей из codex-subagent-execution. Это, по моей оценке, потребует меньше адаптации, чем внедрение полноценного координатора review-loop.*

#KOL-41🎬 __Если делаем свой скилл аналогичный codex-subagent-execution, то какие файлы там должны быть и где они должны лежать? Могут ли лежать только в папках Configs и Sources или там есть обязательные пути?__

*◇ Да, содержимое скилла можно хранить в `Configs` или `Sources`. Но для автоматического обнаружения Codex нужен вход через стандартный каталог скиллов — например, символическая ссылка.*

*Обязателен только `SKILL.md`: YAML-frontmatter с `name` и `description`, затем инструкция оркестратору. Для аналога codex-subagent-execution я рекомендую такой состав:*

- *`Sources/theseus/SKILL.md` — порядок работы, запуск участников, проверки, цикл исправлений и условия завершения.*
- *`Sources/theseus/references/implementer.md` — задание реализатору.*
- *`Sources/theseus/references/spec-reviewer.md` — проверка соответствия Stable.*
- *`Sources/theseus/references/code-reviewer.md` — проверка качества и дефектов.*

*Последние три файла необязательны: сначала все инструкции можно поместить в один `SKILL.md`. Имена файлов шаблонов произвольны; из основной инструкции нужны явные ссылки на них. Собственные скрипты не требуются.*

*Размещение для obsta: папка `Sources/theseus/` содержит оригиналы, а `.agents/skills/theseus` — символическая ссылка на `../../Sources/theseus`. *Просто положить `SKILL.md` в `Sources/theseus/` недостаточно для автоматического обнаружения. Без установки агенту можно прямо поручить прочитать этот файл по пути, но это будет явная загрузка инструкции.*

*Опциональны `agents/openai.yaml` — оформление, политика активации и зависимости; `scripts/` — исполняемые помощники; `assets/` — шаблоны и ресурсы. `agents/openai.yaml` не задаёт роли реализатора и reviewer: их задания можно оставить обычным текстом. Для самостоятельного скилла манифест плагина не нужен.*
