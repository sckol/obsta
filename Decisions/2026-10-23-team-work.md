### *Что мешает параллельной работе сейчас*

*В [[Sources/obstagent.py|текущем watcher]] SQLite хранит только номер и время создания запроса. База находится в системном временном каталоге и привязана к абсолютному пути vault. Общей очереди, владельца запроса и состояния выполнения пока нет. Последовательность дополнительно обеспечивают один watcher и блокировка на весь запуск. Это шире, чем ограничение выбранной БД: SQLite поддерживает несколько подключений на одной машине, но сериализует записи. Для коротких операций очереди этого часто достаточно; транзакцию нельзя держать всё время работы агента.*

*Нужно разделить три вопроса: уникальность ID, право выполнять запрос и объединение изменений документов. Замена SQLite решает лишь часть. Копировать работающий файл базы через Obsidian Sync, облачную папку или Git нельзя считать протоколом общей очереди: независимые копии не согласуют транзакции. Доступ нескольких машин к SQLite через сетевую файловую систему тоже не стоит брать за основу.*

### *Что нужно при любом выборе*

1. *Постоянная идентичность. Отделить задачу, запрос внутри неё и попытку выполнения. Сейчас номер выдаётся на каждую активацию команды; для будущего закрытия задачи из [[2026-10-21-what-to-do-with-git|обсуждения #42]] нужна отдельная связь. Для распределённого создания подойдёт UUID; короткий номер вроде #43 может выдавать общий сервис. Строго возрастающий общий номер офлайн без координации недоступен. Заметке тоже нужен устойчивый ID, чтобы переименование пути не теряло связь.*
2. *Повторная доставка. У активации должен быть постоянный ID, синхронизируемый вместе с запросом: два watcher, увидевшие один запрос, отправляют один ключ. Хеш текста недостаточен — человек может законно повторить ту же команду. Повторное получение события или ответа API не должно создавать новый запуск.*
3. *Назначение с ограниченным сроком. Сервис атомарно записывает владельца и номер попытки; исполнитель продлевает назначение. После истечения срока следующий получает новый номер, а результат прежнего больше нельзя автоматически принять. Это защищает публикацию, но не отменяет уже сделанную shell-команду: неизвестные побочные эффекты после сбоя требуют сверки, а не слепого повтора. При недоступном координаторе новые общие задания не захватываются.*
4. *Изоляция и интеграция. У участника своя копия vault, у параллельного агента — отдельный worktree или checkout с закреплённой базой. Результат содержит базовый коммит и изменения. Отдельный исполнитель последовательно принимает результаты, проверяя актуальную версию и права из [[Протокол работы с агентом-исполнителем]]. Если два агента меняют один фрагмент, второй результат пересматривается; человеческий текст не перезаписывается автоматически. Для начала удобно разрешать один активный агентский запрос на заметку, сохраняя параллельность между заметками.*
5. *Явные этапы: запрос принят → выполняется → результат подготовлен → интегрирован → сохранён. Git-коммит и запись состояния БД не образуют одну транзакцию. Нужны сохранённая ссылка на результат и восстановление после сбоя между шагами; повторная интеграция того же результата не создаёт дубль.*

### *Как это сочетается с предложенной историей Git*

*В #40–41 предложено хранить версии файлов в Git, состояние — в SQLite, а снимки всего vault делать перед запросом и после результата. Для команды полные снимки разных рабочих копий нельзя последовательно накладывать друг на друга: копия Б может ещё не содержать принятую правку А и затереть её. Каждый участник может вести собственную служебную историю, например отдельную ветку участника. В общую историю попадают проверенные изменения относительно закреплённой базы. Служебные ссылки на результаты надо явно передавать на remote вместе с достижимыми объектами: обычная синхронизация Markdown их не переносит.*

*Пример: Анна меняет описание API, Борис — инструкцию запуска. Оба работают от версии V. После принятия результата Анны результат Бориса применяется к обновлённой версии как изменение от V, проверяется и сохраняется. Полный старый снимок Бориса не заменяет общий vault. Если оба изменили одно предложение API, результат Бориса остаётся подготовленным до разбора конфликта.*

### *Предлагаемый следующий шаг*

*Для небольшой команды с сетью рекомендую вариант 1: API координации поверх SQLite, отдельные рабочие копии и один интегратор результатов. База здесь остаётся локальной для сервера; локальная `.obsta/` клиентов хранит только их кэш и незавершённые отправки. Переход на PostgreSQL позже меняет хранение за API, сохраняя договорённости об ID, назначениях и результатах. Если хотим вообще обойтись без сервиса приложения, вариант 3 реалистичен, но строгий захват всё равно потребует доступного общего remote; офлайн можно создавать запросы и готовить предложения, допуская конкурирующие попытки.*

*При реализации сначала проверить два одновременных захвата одного запроса, повторную доставку, возвращение старого исполнителя после истечения назначения, сбой между Git и БД и две правки одной заметки. Здесь предложены альтернативы и протокол; текущая последовательная работа watcher не меняется.*

### *GitHub или Gitea*

*GitHub удобнее, если код и команда уже там: управляемый сервис, привычные PR, проверки и интеграции, меньше собственного администрирования. Цена — зависимость от доступности и правил внешнего сервиса, его API и модели доступа. Содержимое отправляемых запросов и ответов хранится у провайдера; права репозитория могут быть шире прав на отдельные заметки vault.*

*Gitea удобнее, если важны собственный сервер, размещение в локальной сети и контроль над данными. Но обновления, доступность и восстановление Git вместе с БД и вложениями становятся нашей ответственностью. Её API и возможности автоматизации надо проверять для выбранной версии: внешнее сходство с GitHub не означает полной совместимости. Самостоятельное размещение Gitea не устраняет серверную БД, а передаёт хранение реестра готовому приложению.*

### *Как сохранить работу из Obsidian*

*Я бы оставил документы и исходный текст запросов в vault, а в Issues хранил карточку задачи: название, общий статус, ответственного и ссылки на запросы и результаты. Полностью зеркалировать заметку в редактируемое описание issue на первом этапе не стоит. Трекер управляет общими полями карточки, obsta публикует краткие сводки; изменения описания issue не переписывают человеческий текст заметки. Внешние комментарии можно показывать как контекст, а запуск агента требует явного действия уполномоченного участника.*

*Одна issue может объединять несколько запросов obsta, как предполагает [[2026-10-21-what-to-do-with-git|обсуждение #42]]. У задачи, каждого запроса и каждой попытки выполнения должны быть отдельные идентификаторы. Тогда ✅ означает, что конкретный запрос выполнен, а закрытие issue — отдельное решение о завершении задачи. Старые номера #1–44 сохраняем; связь с внешним трекером добавляем отдельно, без перенумерации истории.*

*Запрос получает устойчивый UUID до отправки. Если создание issue завершилось на сервере, но ответ потерялся, перед повтором ищем связь с этим UUID. Это помогает восстановлению, однако поиск с последующим созданием сам по себе не атомарен: два watcher могут одновременно создать дубли. Для первого варианта нужен один отправитель общих запросов, а при восстановлении — сверка и обработка дублей. Локальную SQLite можно оставить для кэша, соответствий ID и очереди неотправленных операций; она перестаёт быть общим источником состояния команды.*

### *Где Issues не заменяют координатор*

*Два агента могут одновременно прочитать «свободно», назначить себя и начать работу. Метка `running`, комментарий «взял» или assignee не дают гарантии единственного запуска. Не следует предполагать, что обычное обновление issue предоставляет атомарную операцию «назначить, только если свободно». Это надо отдельно доказать для конкретного API и протокола.*

*Самый простой старт — один диспетчер, который последовательно принимает запросы и назначает их нескольким исполнителям. Исполнители работают параллельно в отдельных checkout/worktree; диспетчер учитывает попытки и принимает результаты. До запуска повторной попытки после сбоя проверяем прежнюю; если прежний исполнитель может вернуться, его результат нельзя автоматически принять как актуальный. Для нескольких диспетчеров потребуется общий механизм атомарного назначения, например небольшой сервис с БД. Записывать каждое продление назначения комментарием в issue неудобно: это засоряет обсуждение и расходует API.*

*Issues также не объединяют Markdown. Каждый результат должен ссылаться на базовый коммит и подготовленный коммит или PR. Интегратор проверяет изменения на актуальной версии и сохраняет человеческий текст по [[Протокол работы с агентом-исполнителем]]. Для начала можно выполнять одновременно разные заметки, оставляя одну активную попытку на заметку. После сбоя между сохранением результата в Git и обновлением issue надо сверять ссылки и завершать учёт, а не выполнять запрос заново.*

### *Что я бы выбрал*

*Для небольшой команды с постоянной сетью — Issues на той платформе, где уже лежит репозиторий, один диспетчер obsta и отдельные рабочие копии исполнителей. GitHub предпочтителен для быстрого старта без обслуживания сервера; Gitea — при требовании собственного размещения. Такой вариант заменяет разработку общего реестра и командного интерфейса, сохраняя небольшой слой исполнения в obsta. Если нужен только общий счётчик и очередь агентов без человеческой работы в трекере, API поверх SQLite из #43 будет проще по модели данных.*

*Перед внедрением стоит проверить два одновременных создания одного запроса, потерянный ответ API, повтор события, недоступность трекера, сбой диспетчера и конфликт двух результатов в одной заметке. Здесь разобраны плюсы, минусы и предлагаемый порядок работы; миграция остаётся отдельной задачей.*
